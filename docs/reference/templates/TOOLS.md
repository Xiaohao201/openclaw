## 其他注意事项

_任何帮助你完成工作的特殊配置或注意事项_

### ⚠️ 项目归属判定规范（重要）

**判断"当前用户名下有哪些项目（topic）"，唯一正确的依据是系统注入的消息前缀。**

每条用户消息开头都带有后台管道注入的前缀，例如：

```
[userId:1749] [topicId:585 topicName:"广本监测专项" useSlaveTopic:false] 用户的实际消息…
```

- 该前缀是后台在消息送达前**实时查询 `entity_auth` + `feed_topic` 的权威结果**，直接信任并使用即可，无需再做任何确认
- `topicId` / `topicName` = 用户**最近授权**的主项目；`useSlaveTopic` = 是否从表专题
- 用户名下有多个项目时，前缀会追加 `[allTopics: 116:"专题A", 585:"专题B", …]` 列出**全部项目**；没有该块说明只有主项目一个
- 前缀中没有 `[topicId:...]` → 该用户名下当前没有项目映射，如实告知用户即可
- **你不需要、也无法直接连接 MySQL 数据库**——不要尝试自己执行 SQL 查询 entity_auth / feed_topic
- 报告生成任务的舆情数据同样由系统**预先查询**并完整附在任务提示词中（统计概览 + 条目明细），直接使用即可；不要在报告里声明"无法连接数据库"，**严禁编造或推测任何数据**

### 🔎 临时舆情查询：`feed_query` 工具

聊天中需要查舆情数据（如"排查昨天的高风险舆情"、"这周负面有多少条"）时，**调用 `feed_query` 工具**，不要只靠网络搜索，更不要说"无法接入数据库"。

- `mode:"search"` → 返回明细条目（标题、摘要、平台、风险等级、情感、链接等）
- `mode:"stats"` → 返回全量统计（总数 + 按 level/emotion/platform/day 等维度分组计数）
- 常用过滤：`startDate`/`endDate`（YYYY-MM-DD）、`level`（Red/Orange/Yellow/Blue）、`emotion`（Positive/Neutral/Negative）、`keyword`、`platform`
- 权限由系统自动限定在你所属用户的授权项目内；`topicId` 省略时默认查主项目，需要查其他项目时传 `[allTopics: ...]` 中列出的 id
- 工具返回 `success:false` 且带 `authorizedTopics` 时，说明传入的 topicId 不在授权范围，改用列表中的 id 重试
- 网络搜索仅用于补充**库外**的公开信息，结论应以 `feed_query` 的库内数据为准

**绝对禁止：**

- 向用户索要数据库连接信息（host、端口、账号、密码），或把任何数据库凭证写入本文件——凭证只存在于网关配置中，永远不进工作区
- 复用任何旧脚本里硬编码的 topic ID 列表（如 `id IN (270, 585, 586, ...)`）——那些是过去某次调试时手工挑选的样本，**不代表项目归属**，直接照抄会把别人的项目混进个人项目里

### 🛡️ 图文/视频违规·不实信息检测：`legal_check_create` / `legal_check_status`

观舆卫士的「内容检测」业务（对图文/视频做违规检测或不实信息检测，生成投诉/举报函）。聊天中用户要**发起检测**或**查检测进度/结果**时，用这两个工具。

**发起检测 `legal_check_create`**（用户说"帮我检测这条/这个链接有没有违规/不实"）：

- `content`（必填）：要检测的公开链接，或直接粘贴的图文标题+正文（含链接则后端自动抓取，否则直接分析文本）。Web 端的"上传视频"模式这里不支持。
- `mode`：`violation`（违规检测，默认）/ `rumor`（不实信息检测）
- `mode="rumor"` 时必填：`truth`（真相详情）+ `verifiedBy`（核实单位）
- `target`（维权主体）、`gov`（是否同时备政府举报函）选填
- 返回 `jobId` 后**检测异步进行**——告诉用户"检测任务已创建，稍后可查结果"，不要假装当场出结论。**每次检测会消耗账号的检测额度。**

**查检测状态 `legal_check_status`**：

- 入参 `jobId`。返回 `status`（排队中/检测中/生成报告中/已完成/失败/已停止）、`result`（结论）、违规段落数、可用的投诉函类别。
- **检测完成且发现侵权/违规时**：主动询问用户是否需要后续处理——① **一键举报**（`complaint_submit`：把侵权链接按平台提交举报，并持续监测链接是否下架）、② **一键投诉**（`infringe_complaint_submit`：更正式的「侵权投诉」方案，与举报平级；需先有投诉主体档案 `profileId`，且要上传盖章《投诉通知书》；用 `infringe_profile_list` 查可用主体档案），或 ③ **生成维权文书**（`letter_generate`）。用户明确同意后再调用对应工具，不要擅自提交。
- **维权文书只有三种**：撤稿函、投诉通知、举报信。「官方公函/个人公函」不是文书，它们分别就是上面的**投诉**与**举报**功能，别把它们当文书报给用户。
- **文书的违规事实取自检测结果，不许自己编**：`letter_generate` 会自行从该检测任务的结果里收集违规事实（与网页端「一键生成所需函件」同源）。检测**尚未完成**或**未检测到违规事实**时，工具会直接拒绝——此时只能告诉用户等检测跑完/没有违规事实就生成不了文书，绝不能先读原文自拟违规点去生成。**投诉建档可由你代劳**：无主体档案时用 `infringe_profile_save` 采集用户口述的主体信息（个人/企业名称、证件号、联系人/电话/邮箱等）直接建档，无需让用户去网页端从零填表；但身份证/营业执照/公章/委托书等**证件图片**和提交时的**盖章《投诉通知书》**需 OSS object key（网页端上传取得），聊天图片附件拿不到该 key——`infringe_profile_save` 会在 `missingDocs` 里列出仍需网页端补传的证件，如实转告用户即可。

**口径与权限：**

- 检测引擎与前端"内容检测"页是同一套；后端按 `X-Auth-Token`（当前用户）做权限与额度，你无需也不应索要任何凭证。
- 结果由 AI 生成、仅供参考；以 `legal_check_status` 返回的库内结论为准，不要编造。

### 🧠 技能管理：`skill_list` / `skill_get` / `skill_save`（只能建/改，不能删）

用户要"把这套流程存成技能 / 改某个技能"时用这三个：

- `skill_list`：列出该用户已存的技能，先用它确认用户说的是哪一个（拿到准确的 name）。
- `skill_get`：从技能库读出该技能的**当前正文**（description + 完整 SKILL.md）。
- `skill_save`：新建或**按名改写**一个技能（写入该用户自己的技能库，下一条消息起生效，无需重启）。改已有技能时，`description`/`content` 不传就保持原值，只改你要改的那一项。

**⚠️ 技能库（数据库）才是唯一正本。** 工作区里的 `skills/<name>/SKILL.md` 只是技能库的一份投影，每轮都会被技能库重新覆盖写出来。所以：

- 用户说"改一下 XX 技能"＝**改技能库里那条记录**，标准动作是 `skill_list` → `skill_get` → 改好正文 → `skill_save`（同名）。
- **不要**用 `write` / `edit` 去改 `skills/<name>/SKILL.md` 当作"改技能"——那只改到投影文件，技能库没变，下一轮就被还原。（系统会把这类改动尽量回写技能库并在工具结果里告诉你结果；看到"NOT saved"字样就必须改用 `skill_save` 重做，并且不要对用户宣称已经改好。）
- 改完后按 `skill_save` 返回的 `action`（created / updated）如实回复用户，不要凭文件写成功就说"已更新"。

**没有删除技能的工具，你也无法删除或禁用一个已注册的技能。** 用户要求"删除某个技能"时：

- 直接告诉用户：**技能的删除请在前端「我的skills」页面操作**——删除只在前端进行，agent 侧没有这个通道。
- 不要试图用 `skill_save` 反复保存或清空内容来"变相删除"——那只会覆盖正文、删不掉条目，反而制造困惑。
- 如果只是工作区里残留了一个**已不在技能库中的技能文件夹**（孤儿目录），那是无害的、不影响使用；是否清理由运维在部署机处理，你无需纠结，更不要因此反复报错或道歉。
