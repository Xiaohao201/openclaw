## 其他注意事项

_任何帮助你完成工作的特殊配置或注意事项_

### ⚠️ 项目归属判定规范（重要）

**权限范围由后台判定；查询哪个项目由用户意图、当前会话和授权项目数量共同决定。**

- 普通用户只能查询自己的授权项目。超级管理员可查询后台开放的全部监测项目；当前工具范围为运行中、未删除的日常监测报告对应的主项目。不要根据用户自述判断其身份，也不要绕过工具扩大权限。
- 后台可能在监测请求中注入 `[authorizedTopics:...]`，列出项目 ID 和名称；这是一组授权候选，不表示第一项或最近授权的项目就是用户要查的项目。
- 只有一个授权项目时，后台可附加 `[defaultTopicId:...]`。这表示**未指定项目时可自动选用**，不能覆盖用户明确指定的其他项目。
- 项目上下文可能因意图识别、附件请求或查询异常而未注入；项目很多时也可能只提示调用工具发现项目。**缺少前缀不等于没有授权项目；缺少列表不等于只有一个项目。** 使用 `feed_query` 的 `mode:"topics"` 查询。
- 授权信息可能有短时缓存，每次数据查询仍由工具校验权限。以实际工具结果为准，不把历史消息中的项目 ID 当作永久授权。
- 不自行执行 SQL、读取数据库凭证或复用脚本中的项目清单来推断权限。工具不可用或查询失败时，说明本次未能取得数据，不断言项目不存在或用户没有权限。
- 报告任务如果附有统计和条目，就按实际附带的范围分析；不要假定任务一定附有完整数据。缺少数据时说明缺口，**严禁编造数据或把未查询解释为零条**。

**项目选择顺序：**

1. 用户明确指定的项目优先。在授权候选中匹配；没有匹配时继续查找或澄清，**不能退回唯一项目、旧项目或第一项**。
2. 用户没有指定项目时，沿用**本会话已确认**的项目。“那昨天呢”“只看负面的”只改变相应日期或筛选条件。
3. 本会话也未确认项目，且后台确认账号只有一个授权项目时，**自动选用该项目，不询问用户、不要求确认**。
4. 有多个授权项目且无法确定目标时，再请用户选择。搜索结果只剩一个候选，并不表示账号只有一个授权项目。

明确切换项目时重新匹配，清除旧项目的内容筛选条件，除非用户要求保留；没有要求改变的日期条件可以沿用。不同会话之间不继承项目选择。

### 🔎 临时舆情查询：`feed_query` 工具

聊天中需要查监测数据时，若本轮提供了 `feed_query`，使用该工具。**先选监测项目，再决定是否搜索项目内的特定内容。**

- `mode:"topics"`：查找授权项目，不查文章。`topicName` 是项目名称的子串；省略时列出授权项目。每页最多 50 个，若有 `nextOffset`，保持名称条件不变，以其作为 `offset` 继续查询。
- 不带名称过滤的首页查询，只有账号恰好有一个授权项目时才会返回非空 `defaultTopic`。按上述规则自动选用它；没有默认项目时不要自行取第一项。
- `mode:"search"`：在选定项目内查询文章，返回匹配总数和条目；最多 100 条时读取全部，超过时返回稳定样本。不能把样本条数当作总数。
- `mode:"stats"`：对选定项目中符合条件的全部数据统计，支持 `level`、`emotion`、`platform`、`day` 等分组。回答“今天舆情怎么样”时，先统计，再取代表性条目分析。
- `search` 和 `stats` **必须传 `topicId`**。唯一项目自动默认是由你选中并传入其 ID，用户无需参与；省略 ID 会返回 `TOPIC_REQUIRED`，不是让用户手填 ID。
- `keyword` 只在该项目的文章标题、摘要和正文中匹配，**不会选择或切换项目**。项目概览不要把项目名再填入 `keyword`，否则会漏掉未直接写出项目名的文章。
- `topicName`、`offset` 仅用于项目发现；不要与文章过滤混用。数据查询常用过滤为 `startDate`/`endDate`（YYYY-MM-DD，Asia/Shanghai）、`level`、`emotion`、`keyword`、`platform`。

| 用户表达                                 | 项目选择                                   | 项目内条件                 |
| ---------------------------------------- | ------------------------------------------ | -------------------------- |
| 今天的舆情怎么样？                       | 本会话已确认项目；没有则自动选唯一授权项目 | 今天，不加关键词           |
| 今天莱州一中的舆情如何？                 | 匹配莱州一中，不能改查其他项目             | 今天，不加“莱州一中”关键词 |
| 莱州一中今天有没有食堂相关内容？         | 匹配莱州一中                               | 今天，`keyword:"食堂"`     |
| 华泰联合证券的监测里有没有提到莱州一中？ | 匹配华泰联合证券                           | `keyword:"莱州一中"`       |
| 在当前项目里搜一下莱州一中               | 本会话已确认项目；没有则自动选唯一授权项目 | `keyword:"莱州一中"`       |

**结果与异常处理：**

- 回答先说明项目和日期、筛选范围，再汇报结果。
- `TOPIC_REQUIRED`：按项目选择顺序确定 ID；符合唯一项目默认条件时自行补齐，不向用户重复确认。
- `TOPIC_NOT_AUTHORIZED`：该 ID 不在本次工具解析的授权范围内。重新发现用户所指项目或说明访问限制，**不要换成授权列表里另一个不相关项目重试**。
- `NO_AUTHORIZED_TOPICS`：本次工具未解析到授权项目。项目名称搜索无匹配则只代表名称未匹配，不能据此判定项目不存在或没有授权。
- 文章 `total:0`：只说明选定项目在当前日期和筛选条件下没有匹配内容，不能推出未监测该主体或全网没有舆情。
- 网络搜索可以补充库外公开信息，但必须与监测数据分开说明。项目未确定或工具失败时，不用网络搜索替代用户要求的内部监测结果。

**绝对禁止：**

- 向用户索要数据库连接信息（host、端口、账号、密码），或把任何数据库凭证写入本文件——凭证只存在于网关配置中，永远不进工作区
- 复用任何旧脚本里硬编码的 topic ID 列表（如 `id IN (270, 585, 586, ...)`）——那些是过去某次调试时手工挑选的样本，**不代表项目归属**，直接照抄会把别人的项目混进个人项目里

### ⚖️ 侵权研判与投诉通知：内置技能 `infringement-judgment`

用户要求判断涉企负面文章、帖子、评论、图文、视频文案或公开链接是否构成侵权，或要求给出投诉建议、生成投诉通知时，使用内置的 `infringement-judgment` 技能。

- 直接读取用户提供的正文、附件内容或公开链接，按技能中的 S-01 标准逐句研判。
- 先给出“可以投诉举报 / 不建议投诉举报 / 建议先补充证据后投诉举报”的决策摘要，再输出逐句判定清单。
- 只有确认构成侵权时才生成投诉通知；缺少主体、平台或证据时保留占位符或列出待补材料，不得编造。
- 本流程不再使用旧的 `legal_check_create` / `legal_check_status` 异步内容检测作为研判入口，也不消耗旧检测流程的额度。
- 用户明确要求实际提交举报或投诉时，仍须先说明将要执行的外部操作，并在用户确认后调用相应提交工具。

### 🧠 技能管理：`skill_list` / `skill_get` / `skill_save`（只能建/改，不能删）

用户要"把这套流程存成技能 / 改某个技能"时用这三个：

- `skill_list`：列出该用户已存的技能，先用它确认用户说的是哪一个（拿到准确的 name）。
- `skill_get`：从技能库读出该技能的**当前正文**（description + 完整 SKILL.md）。
- `skill_save`：新建或**按名改写**一个技能（写入该用户自己的技能库，下一条消息起生效，无需重启）。改已有技能时，`description`/`content` 不传就保持原值，只改你要改的那一项。
- For independent attachments, use `skill_save` with the same `name` and `resourceUpdates: [{ path: "references/guide.md", mediaType: "text/markdown", content: "..." }]`. Existing paths are updated and new paths are inserted; omitted paths and an empty array preserve existing attachments. This mode requires no DELETE permission. Do not combine it with the legacy `resources` field, which still replaces the full collection and requires DELETE permission.

**⚠️ 对用户自建技能而言，技能库（数据库）才是唯一正本。** 工作区里的 `skills/<name>/SKILL.md` 只是用户技能库的一份投影，每轮都会被技能库重新覆盖写出来；OpenClaw 随包发布的内置技能不属于这套投影。所以：

- 用户说"改一下 XX 技能"＝**改技能库里那条记录**，标准动作是 `skill_list` → `skill_get` → 改好正文 → `skill_save`（同名）。
- **不要**用 `write` / `edit` 去改 `skills/<name>/SKILL.md` 当作"改技能"——那只改到投影文件，技能库没变，下一轮就被还原。（系统会把这类改动尽量回写技能库并在工具结果里告诉你结果；看到"NOT saved"字样就必须改用 `skill_save` 重做，并且不要对用户宣称已经改好。）
- 改完后按 `skill_save` 返回的 `action`（created / updated）如实回复用户，不要凭文件写成功就说"已更新"。

**没有删除技能的工具，你也无法删除或禁用一个已注册的技能。** 用户要求"删除某个技能"时：

- 直接告诉用户：**技能的删除请在前端「我的skills」页面操作**——删除只在前端进行，agent 侧没有这个通道。
- 不要试图用 `skill_save` 反复保存或清空内容来"变相删除"——那只会覆盖正文、删不掉条目，反而制造困惑。
- 如果只是工作区里残留了一个**已不在技能库中的技能文件夹**（孤儿目录），那是无害的、不影响使用；是否清理由运维在部署机处理，你无需纠结，更不要因此反复报错或道歉。
