# 三个插件的受管交接改造方案

日期：2026-10-28。目标分支：v3。状态：插件交接代码已实现；原始设计与实施差异见下文，实际验收范围见 `managed-plugin-handoff-validation.md`。本稿中的计划用例不等于全部完成的生产验收。

### 实施决策记录

- 执行服务采用显式 v2 契约及宿主能力检查，避免旧宿主忽略阶段字段。既有 v1 服务维持入口阶段语义。
- 当前先等待入口排空和全局空闲，再关闭核心准入、排空执行插件；不引入可伪造的内部请求标记。持续从独立入口进入的新任务可能推迟空闲窗口，此时升级超时并恢复旧实例，不强行打断任务。提前关闭所有顶层入口并传播可信延续上下文留待独立实现。
- 已检查 acpx 0.5.3：持久会话 ensure 后可能缓存客户端，没有公开的无损 dispose。已 ensure 但尚未完成执行轮次的会话会阻止交接并恢复旧实例；不通过私有字段、删除会话或盲杀进程规避。运行流即使被消费者提前关闭，适配层仍等待生产者真正结束。
- 插件改造不改变 Windows 系统权限。系统级禁止夙衡或 ACP 子进程终止同账户服务，仍需要独立权限隔离部署，不能通过本次代码宣称已经满足。

适用部署：Windows 单机、手动命令启动外部 supervisor，Web 请求经 RabbitMQ 进入 Gateway。对应服务为 `acpx-runtime`、`browser-control`、`device-pair-notifier`。

## 1. 问题与交付目标

用户提供的日志显示，`gateway supervise` 已被识别，启动过程进入插件加载，但上述三个服务被拒绝：`Externally managed services require the v1 handoff contract`。当前代码的服务管理器会记录这些启动失败，使受管服务总体 readiness 无法通过。日志中的 Gateway ready 并不代表全部受管插件就绪；所提供片段也不足以证明 supervisor 最终以哪种错误退出。

本次要实现的不是仅让报错消失，而是让三个服务遵守“待命启动、停止接收新工作、等待已接工作完成、恢复、最终释放”的交接协议。

交付目标：

- 首次受管启动时，三个插件可以初始化到待命状态；由 supervisor 决定何时放行工作。
- 更新时，旧实例已接收的任务继续完成，新实例不会提前消费、执行浏览器操作或发送通知。
- 候选实例失败、旧实例排空超时时，交接状态可诊断，按现有提交边界恢复服务。
- 普通 `gateway run` 仍保持现有启动行为，不强制要求用户改为受管模式。
- 夙衡不获得关闭或重启自身服务的能力。生命周期决策仍属于外部 supervisor。

本次不承诺迁移运行中的 Node 内存、ACP 流或 WebSocket 连接，也不承诺所有浏览器页面跨进程切换原样保留。Web/RabbitMQ 入口可利用队列覆盖切换间隙，但实际交付语义仍取决于消息确认、重投与业务幂等。

## 2. 已核查的实现缺口

| 服务                   | 当前行为                                                                                           | 必须补齐                                                             |
| ---------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `acpx-runtime`         | 注册后端后异步探测；stop 注销后端；包装层直接返回执行流                                            | 待命门禁、探测状态、完整执行流计数、排空及资源释放确认               |
| `browser-control`      | 默认懒加载 HTTP server，也支持进程内 control service；停止时清理浏览器运行时；插件层吞掉 stop 错误 | 覆盖进程内与 HTTP/RPC 路径的门禁、真实操作计数、排空、可见的清理失败 |
| `device-pair-notifier` | 启动立即轮询；定时回调可能重叠；stop 仅清除定时器                                                  | 待命不发送、单次轮询互斥、等待在途发送和持久化、恢复防重入           |

代码依据：`extensions/acpx/src/service.ts`、`extensions/acpx/src/runtime.ts`、`extensions/browser/src/plugin-service.ts`、`extensions/browser/src/control-service.ts`、`extensions/browser/src/browser/runtime-lifecycle.ts`、`extensions/device-pair/notify.ts`。

另有两个共享层问题需要随改造处理：

1. `src/plugins/services.ts` 当前并发暂停所有服务。若先关闭 ACP/浏览器，新工作虽被阻止，已经接收的 RabbitMQ 任务却可能在后续步骤需要它们，导致排空失败。
2. 激活过程的父进程调用超时与子进程启动、就绪等待预算不完全一致。全插件冷启动时，必须区分启动慢、依赖不可用和缺少交接契约，不能只增大 timeout。

## 3. 统一交接模型

### 3.1 状态与方法语义

状态采用明确枚举：`starting → standby → active → quiescing → paused → stopped`，另设 `failed` 并保留结构化原因。

| 方法      | 要求                                                                          |
| --------- | ----------------------------------------------------------------------------- |
| `start`   | 受管模式初始化后进入 standby；普通模式正常进入 active。失败必须保留可清理句柄 |
| `isReady` | 表示初始化完成且具备接管条件；standby 可以 ready，但不能执行用户工作          |
| `pause`   | 阻止未获准的新工作，等待已经获准的操作真正结束；超时不等于取消业务任务        |
| `resume`  | 幂等打开入口；失败不得留下重复定时器或重复注册                                |
| `stop`    | 最终释放资源；清理失败向上报告，不通过吞错伪装成功                            |

异步操作使用代次号和显式状态，避免上一代探测、轮询或清理回调修改新一代状态。并发 pause/stop 共享执行中的 Promise，避免重复释放。

显式禁用与启动失败必须区分。配置关闭的服务可以报告“禁用且已就绪”；探测失败、未初始化、未知懒加载能力不能借用禁用状态通过 readiness。

### 3.2 排空顺序：先关入口，再关执行能力

推荐采用以下顺序：

1. 候选进程完成可无副作用执行的预检；不消费消息、不运行通知、不占用旧实例的独占资源。
2. 旧实例停止 RabbitMQ 新消费、调度器新任务和其他自主入口；关闭 Gateway 新顶层任务接收。
3. 旧实例继续执行已经接收的任务，包括其后续 ACP、浏览器调用及回复持久化。
4. 已接任务完成后，暂停执行服务，等待其内部流、浏览器操作、通知发送及文件写入归零；再次检查全局空闲。
5. 旧实例释放 Gateway 独占资源；候选实例取得所有权并以 standby 激活。全部 readiness 通过后，由 supervisor 提交并恢复入口。
6. 外部 supervisor 按现有协议回收旧进程；插件和夙衡均不调用自身进程退出或重启。

这里需要一个通用的分阶段接口，不能在核心按三个插件 ID 写特殊分支。建议在现有 v1 契约上增加可选能力声明 `drainPhase: "ingress" | "execution"` 和可选的入口关闭钩子；保留现有 `pause/resume/isReady` 语义。既有 v1 服务默认 ingress，新执行服务显式声明 execution。接口名称在实现前结合 SDK 类型评审确定，能力必须可检测，不能让旧宿主静默忽略关键能力后仍接受插件。

**只有阶段字段仍不够。** 浏览器兼有独立外部请求和已接任务的内部调用：前者应先关闭，后者应继续完成。需要宿主提供已接任务的延续凭证或等价的可信上下文，并将其传播到相关工具调用。凭证由宿主创建、在任务结束时失效，外部 HTTP/RPC 参数不能自行声明拥有凭证。不能简单允许所有“本地请求”绕过门禁。

实现第一步先核查现有任务上下文能否完整覆盖这些调用路径；若不能，先补通用宿主上下文接口和回归测试，再接入插件。这是交付前置条件，不以固定等待几秒替代。对于独立 browser/node-host 进程，应按其自身生命周期处理，不把远端操作错误计入本机已排空。

### 3.3 失败恢复边界

- 旧实例排空超时：不强杀业务任务，终止本次切换并恢复旧实例入口，报告阻塞服务及在途数量。
- 候选实例未提交前失败：确认候选释放资源后，按现有 coordinator 流程恢复旧实例。
- 候选已提交且可能处理工作后：不自动切回旧实例，以免出现双消费；保留候选实例，提供明确的恢复状态。
- 停止失败：标记清理未完成，不能据此宣告资源已释放。对浏览器/ACP 外部进程，不能仅凭 Gateway 子进程退出推断资源已经清理。

## 4. 各插件的具体改造

### 4.1 ACP：追踪执行流，保留会话语义

在 OpenClaw 插件适配层维护初始化状态、接单门禁与在途操作集合。基础 ACP runtime 继续由 `acpx/runtime` 提供，不复制其通用实现。

- 将 availability probe 保存为可等待的初始化任务。受管 readiness 依赖明确的探测结果；探测失败包含服务 ID、原因和修复建议。
- `runTurn` 的计数覆盖整个 `AsyncIterable` 生命周期，而不是创建迭代器时就算完成。验证正常结束、抛错、消费者提前 return、调用取消后的实际收尾。
- `ensureSession`、状态修改、会话关闭及持久化等会影响一致性的操作纳入计数。只读诊断是否允许在 paused 中执行，要形成显式允许列表。
- quiescing 阶段允许已有宿主任务的后续操作；standby/paused 拒绝新的执行。错误使用可识别的状态码，不依赖日志字符串判断。
- pause 等待操作结束，不通过 cancel/close 强行截断用户任务。stop 在排空后注销后端，等待探测收尾并释放本实例拥有的资源。
- 不为了升级删除持久化会话。新进程重新加载会话记录；能否恢复底层 ACP 会话须通过依赖实际行为验证，不能承诺转移正在输出的流。
- 核查底层依赖是否有足够的进程清理接口。若缺少，按 ACPX 本地指南在上游补通用能力，再消费正式版本；不能通过访问私有字段或盲杀进程补齐。

`OPENCLAW_SKIP_ACPX_RUNTIME` 与跳过探测的选项分别测试。受管模式下，仅跳过探测不应自动证明后端健康；生产必须有明确的可用性验证策略。

### 4.2 浏览器：统一操作门禁，区分资源所有权

加载器优先选择进程内 control-service 导出，但当前默认 `server.ts` 模块实际启动 HTTP 控制服务，真实构建烟测已确认这一点。两种路径以及 Gateway 的进程内分发都需要受控，因此只在 Express 中添加中间件不能完成交接支持。

- 在插件内部引入生命周期控制器，覆盖 local dispatcher、Gateway browser request、HTTP 路由和本机 node-host 路径；共用操作租约，避免同一次调用嵌套计数或漏计。
- 入口关闭后拒绝新的独立请求；合法的已接任务延续调用可继续。最终 pause 关闭所有业务准入，并等待租约归零。
- 计数跟随底层浏览器操作真实完成。调用方超时或 `Promise.race` 提前返回，不代表浏览器操作已经结束。
- standby 仅做允许的初始化；不能提前导航、点击、启动用户任务，或争抢仍归旧实例所有的 profile。
- readiness 表示控制运行时初始化完成且入口处于可控状态，不要求为了健康检查启动所有浏览器 profile。
- 显式区分本实例启动的 Chrome、连接外部 CDP 的浏览器以及仅持有的 Playwright 连接。只释放自己拥有的资源，不关闭用户独立启动的浏览器。
- 第一阶段保证正在执行的浏览器操作完成后再交接。对于本实例管理的 Chrome，若切换需要关闭重建，应明确告知页面内存状态可能丢失。浏览器进程独立托管及跨 Gateway 继承所有权属于后续能力。
- 懒加载句柄增加可选且可检测的生命周期能力。普通模式继续支持旧模块；受管模式下，自定义模块缺少能力时明确报不兼容，不伪造 handoff。
- 移除受管清理路径的无条件吞错；逐层区分可忽略的“已关闭”和真正释放失败，保留现有浏览器认证与安全检查。

### 4.3 配对通知器：单次轮询与发送后落盘

- 受管 start 初始化状态与路径，不执行首次 tick，也不创建活跃轮询。
- resume 启动至多一个轮询链；采用“本次完成后安排下次”或 single-flight 防重入。
- pause 清除下一次调度，等待当前 tick 完成，包括远端发送与通知状态保存。不使用 timeout 伪装发送已取消。
- stop 复用排空逻辑，确认无待写状态；代次检查避免旧回调再次安排定时器。
- 通知 tick、订阅命令和一次性通知设置共享状态文件的串行更新机制，避免 read-modify-write 相互覆盖。写入采用原子替换，并测试失败后状态恢复。
- 无订阅、未配置通知渠道时保持空闲可用；不要求 Web/RabbitMQ 用户必须配置 Telegram。暂时的通知网络错误可按已有语义重试，但文件初始化失败不能报告 ready。
- 保持现有设备配对审批权限不变。本次只改通知调度和状态一致性。

正常交接要做到旧实例发送落盘完成后新实例才开始轮询。远端发送成功但本机在落盘前崩溃，仍可能产生重复通知；本次不宣称跨系统 exactly-once。未来若需要该保证，须依赖发送端幂等键或独立 outbox 协议。

## 5. 共享层与诊断改造

| 范围                                          | 计划变化                                                             |
| --------------------------------------------- | -------------------------------------------------------------------- |
| `src/plugins/types.ts`、公开 SDK              | 可检测的分阶段能力与必要任务上下文；兼容现有 v1 和普通模式           |
| `src/plugins/services.ts`                     | 注册完成后先校验全部服务契约，再启动服务；按阶段排空；汇总结构化状态 |
| `src/gateway/server.impl.ts`、生命周期 worker | 顶层任务准入与延续调用区分；协调调度器、入口和执行服务；二次空闲检查 |
| `src/gateway/lifecycle/process-worker.ts`     | 统一父子进程阶段预算、超时分类及阻塞原因                             |
| `src/plugins/lazy-service-module.ts`          | 可选生命周期能力解析，保留原有懒加载边界                             |
| 三个插件及其测试                              | 落实第 4 节行为，不直接导入核心私有模块                              |

契约校验至少检查 version、必需方法和声明能力；未知版本不能仅凭存在 handoff 对象通过。运行时服务注册发生在插件加载后，因此不能声称所有错误都能在无副作用 preflight 发现；预检与激活的职责应在日志中明确区分。

每个阶段设单调时钟 deadline；同一进程内部传剩余预算。跨 IPC 不直接比较两进程的单调时钟时间戳，由父进程保持最终上限并传剩余时长，子进程再建立本地 deadline。进度日志不自动延长预算。

日志至少包含候选版本/进程标识、阶段、服务 ID、状态、耗时、在途数量和结构化失败码。区分 `gateway transport ready` 与 `managed services ready`。不记录凭证、消息正文或个人数据。控制台资源首次构建、依赖探测等耗时应归属明确阶段。

## 6. 夙衡不能关闭或重启自身服务

三个插件都只响应外部生命周期协调，不新增 restart/stop 工具，不调用 `process.exit`、自身 PID kill 或服务重启命令。保留已有外部生命周期标志与工具限制。

应用层限制与系统权限隔离需要分别验收：若夙衡或其 ACP 子进程仍拥有与 supervisor 相同的系统权限，单靠工具过滤无法形成“绝对不能停止自身服务”的安全边界。ACP 自带的执行工具也不能假定自动受到 Gateway exec 工具过滤保护。

生产硬约束需要独立 supervisor 账户/权限与受限工作进程执行环境，限制结束 supervisor、修改启动配置或写入部署程序的权限。当前手动命令行同账户部署不能据此宣称已实现该系统级隔离。本插件方案保留这一部署前置条件；后续应单独给出 Windows 权限方案并验证，而不是在插件中添加自我保护式重启。

## 7. 验证与验收

### 单元与契约测试

- 三个服务：standby 无业务副作用，重复 resume/pause/stop 幂等，半初始化失败可清理，超时不使计数提前归零。
- ACP：流正常结束、错误、提前 return、取消收尾、探测失败、晚到回调、会话保存失败。
- 浏览器：进程内及 HTTP/RPC 入口均受控，客户端超时后底层操作仍被追踪，外部浏览器不会被关闭，清理失败可见，自定义模块缺少能力明确失败。
- 通知器：慢发送跨越多次周期仍无并发 tick，暂停等待落盘，恢复无双定时器，订阅命令与轮询不丢更新，网络和写盘失败可重试。
- 宿主：排空中的任务在后续步骤调用 ACP/浏览器仍成功；新的顶层任务被挡住；伪造延续身份不能绕过门禁。
- 兼容性：普通模式、已有 v1 插件、显式禁用、未知契约版本、未知懒加载能力分别覆盖。

### 集成与故障注入

使用隔离状态目录、测试队列、测试浏览器 profile 和模拟通知接收端，保持三个插件全部启用；不能通过关闭插件获得“交接成功”。先在可重复的模拟依赖上验证时序，再在 Windows 和真实 ACP/浏览器依赖上执行受控联调。

关键场景：

1. 首次启动：三个服务完成待命，收到 resume 后才开始工作。
2. 空闲升级：新旧 PID 不同，候选 release/构建标识符合目标，旧 PID 最终退出。
3. 忙碌升级：RabbitMQ 已接任务正在调用 ACP/浏览器，同时通知器正在发送；全部完成并持久化后才切换，队列中的后续任务由新实例处理。
4. 候选失败：依赖缺失、启动异常、占用资源或初始化超时，旧服务按提交边界恢复，无双消费。
5. 排空超时：保留旧任务和旧实例，日志显示具体阻塞操作，不强杀业务。
6. 提交后恢复失败：不自动回滚产生双消费，操作员可依据状态恢复候选实例。
7. 同一全插件配置反复交接：无残留计时器、注册项、连接或受管外部进程；记录实际停顿时长，不以预设毫秒数作为未经验证的承诺。

预期验证命令包括相应范围的 `pnpm test <path-or-filter>`、ACP 指南要求的 `pnpm test:extension acpx`、`pnpm tsgo`、格式/静态检查和 `pnpm build`。懒加载变更必须检查构建警告。SDK 若新增公开契约，按仓库流程生成并审查 API 基线变动；不能修改测试预期或基线来掩盖错误。

以上是计划中的验收工作，本设计稿没有把尚未执行的测试记为通过。

## 8. 实施顺序与完成判定

1. **共享交接基础**：验证现有任务上下文，先写“旧任务稍后仍需调用执行插件”的回归测试，再补分阶段准入和契约校验。
2. **三个插件适配**：先通知器，再 ACP，最后浏览器多入口；各自先补失败用例，再实现门禁与排空。
3. **诊断及预算**：统一父子进程阶段超时，补各服务状态和失败路径。
4. **完整联调**：使用与实际部署一致的已启用插件集合执行首次启动、升级、故障恢复；验证目标构建确实由新进程运行。
