状态：Windows + Control UI + RabbitMQ 的稳定入口、单活交接、请求恢复和启动失败回滚已加入代码；已开展隔离子进程验证，尚未完成真实 RabbitMQ/MySQL 及生产切换验收。

## 0. 实际部署范围与当前实现边界

用户确认：部署环境为原生 Windows，入口为直接访问端口的 Control UI 和 RabbitMQ，目前没有独立测试环境。

针对该范围的可行性结论：可以实施单机双实例发布，但必须先新增稳定入口、实例协调和 Gateway 排空协议。当前应用不能直接作为无状态双活服务运行。首次将现有 Gateway 端口交给稳定入口需要一次迁移；不能声称首次安装就能透明接管正在使用的端口。

RabbitMQ 已使用手动确认且在处理结束后 ack，但同一会话的串行队列属于进程内状态。`session-snapshot.ts` 从本地上一份 JSONL 复制完整上下文；MySQL 展示历史不是模型会话的替代品。因此正式接管必须复用最终本地会话状态和工作区，且只有一个生产消费者执行。

本轮基础代码改动：

- `RabbitMqClient.stop()` 先关闭新消费入口、取消消费者，再等待已接收的处理完成和确认，最后关闭连接。停止过程中的晚到消息重新入队，重连等待可被唤醒；禁止停止尚未完成时重新启动同一客户端。
- `scripts/deploy-prepare.ts` 从固定的已提交 HEAD 导出到新目录，执行锁定依赖安装、后端/UI 构建和内置产物 smoke。输出必须在源目录之外，且不能已经存在；失败不会触发 Gateway 操作。未提交改动不会进入构建，需要在正式使用前先提交。
- `scripts/deploy-artifact.ts` 写入和验证后端/UI 文件清单及 SHA-256，同时记录平台、架构、Node 主版本和提交。它不证明 node_modules 可移植、不验证生产凭证，也不替代业务 readiness 或完整产物签名。
- `deploy-server.cmd` 改为显式模式，默认不再修改运行目录；`legacy-restart` 是有中断的旧模式，不能作为蓝绿发布使用。

开发/构建机用法（父目录须已存在；示例目录与源码目录必须不同）：

```powershell
pnpm deploy:prepare --output C:\openclaw-releases\candidate-001
pnpm deploy:verify C:\openclaw-releases\candidate-001
```

也可使用 `deploy-server.cmd prepare <目录>` 或 `deploy-server.cmd verify <目录>`。这两个命令仅准备/检查产物，不启动候选实例、不切流、不停止生产服务。若在生产电脑执行构建，资源竞争仍存在，应优先在外部 Windows 构建机执行。

后续实现已补入 `scripts/deploy-supervisor.ts`、`scripts/deploy-proxy.ts`、`scripts/deploy-coordinator.ts`、`src/deployment/worker.ts` 及 Gateway/UI 生命周期代码。现在采用固定 HTTP/WebSocket 入口、IPC 待命进程、同一配置的 Gateway 锁、旧进程退出后激活新进程、候选失败后顺序回滚。可执行说明与准确边界以同目录 `windows-managed-deployment-runbook.md` 为准。

特别注意：托管 worker 使用新加的独立排空流程，不经过普通 CLI stop 的退出时限。排空失败保持关闭新请求的状态，不强杀旧实例来激活新实例。当前消费者仍保留原有业务异常 nack 策略，不提供任意外部工具操作的恰好一次保证。

回归使用模拟 AMQP、临时文件、随机本地端口和真实子进程，不连接生产 RabbitMQ/MySQL，不应将生产用户会话作为测试数据。下文第 1 节起保留原始完整设计目标供追溯，其中持久化收件箱、跨进程请求结果账本、任意渠道无损交接、排空中取消并恢复原进程及严格不断线并未在本轮实现；不能把这些目标当作现有能力。当前实现选择短暂重连、仅重试明确未执行的请求，未知结果恢复草稿供核对。

已完成验证：63 项范围回归测试通过（Windows 部署入口 6 项、构建及产物校验 19 项、RabbitMQ 生命周期/顺序/会话快照 38 项）；`pnpm tsgo`、范围 lint、格式检查通过。独立构建脚本行覆盖率 93.2%，RabbitMQ 客户端行覆盖率 96.99%。这些是模拟依赖和临时文件测试，不代表真实 Windows 双实例端到端验收通过。

## 1. 结论

单机双实例适合作为本项目的发布改造方向，但当前代码不能只靠两个端口和反向代理实现同一业务的无缝切换。

目前支持的是配置、状态、工作区隔离的多个 Gateway。两个完整实例同时使用生产状态和渠道账号，不属于已验证的运行方式。现有会话文件锁解决了部分并发写入问题，但没有解决整个发布周期中的任务归属、消息接收、流式连接和后台任务交接。

建议采用：**外部构建不可变产物，部署机运行蓝绿两个实例，待命实例预热，旧实例排空后交接唯一业务执行权。** 第一阶段保持全局单活，不同时让两个实例处理生产对话，降低会话与长期记忆分叉风险。

“不中断”需要分开验收：

| 目标 | 当前情况 | 改造要求 |
| --- | --- | --- |
| 构建不影响线上进程 | 同机构建仍争抢资源 | 在开发机或 CI 构建；部署机只接收产物 |
| 当前回答正常完成 | 重启路径有有限时间排空，停止路径不同 | 增加独立排空与退役流程，超时默认取消发布 |
| 切换期间新消息不丢 | 现有排空会拒绝新任务 | 稳定入口持久化接收、排队、去重和确认 |
| 下一轮读到最新记忆 | 隔离实例有不同状态；共享目录不能独自保证一致性 | 单写者交接、最终落盘、缓存失效、稳定会话标识 |
| WebSocket 始终保持连接 | Gateway 关闭会主动断开连接 | 若严格要求连接不断，需要独立协议入口；普通代理不够 |

短暂排队不等于消息丢失，但也不等于响应延迟完全不变。单机资源故障不在本方案的可用性保证范围内。

| 位置 | 已确认行为 | 对方案的影响 |

| `src/infra/gateway-lock.ts`，`resolveGatewayLockPath` | 锁文件名称由配置路径的哈希确定 | 使用同一配置路径时，改端口并不能避开实例锁；不能删除锁或强制绕过 |

| `src/config/sessions/store.ts`，`updateSessionStore`、锁队列 | 更新在文件锁内重新读取；写入使用会话写锁 | 已有跨进程文件级保护，应复用，但它不是全业务单活协议 |

| `src/process/command-queue.ts` | 队列和排空标志在进程内；排空时拒绝新入队 | 不会自动把消息转给另一个实例，也不是持久化收件箱 |
| `src/cli/gateway-cli/run-loop.ts` | restart 等待任务和 embedded runs，默认排空上限 300 秒；超时继续重启并尝试中止运行；stop 不进入该排空分支 | 不能把普通 stop、SIGTERM 当作保证当前回答完成的蓝绿退役命令 |

| `src/gateway/server/readiness.ts`、`server-http.ts` | 有健康和 readiness 探针，readiness 检查渠道健康 | 现有探针不证明获得执行权或完成状态交接 |

## 3. 推荐架构

```text
开发电脑 / CI
    └─ 安装锁定依赖 → 测试 → 构建 → 打包 → 校验清单
                                      │
部署电脑                              ▼
    固定业务入口 / 持久化消息接收层（独立生命周期）
                  │
        部署协调器 + 唯一执行权
                  │
        ┌─────────┴─────────┐
        │                   │
    蓝实例：ACTIVE      绿实例：STANDBY
    独立版本目录        独立版本目录
    独立进程配置        独立进程配置
    端口 18789          端口 19001
        │                   │
        └── 业务状态：仅持有执行权的实例允许写入 ──┘
```

图中协调器、生命周期状态、持久化收件箱和执行权协议是拟新增能力，不是当前配置项或 CLI 命令。两个 Gateway 实例之外，还需要稳定入口及协调职责；可以合并实现这些职责，但它们不能随被替换实例一起退出。

端口只是示例。还要核对 browser control、CDP 等所有派生端口，不能只检查两个主端口。容器内的端口、路径和 PID 命名空间也要单独验证。

### 3.1 状态分离

- **发布产物**：每个版本独立且部署后只读，禁止覆盖正在运行的 `dist`、依赖及 UI 资源。
- **实例状态**：日志、临时文件、端口、进程配置、预热缓存独立。
- **业务状态**：会话映射、会话 JSONL、摘要、长期记忆、业务工作区、任务与投递记录由当前 active 实例持有写入权。
- **敏感运行状态**：渠道凭证、设备配对和认证信息走已有受控加载路径，不能进入构建产物；待命实例不得因此提前连接生产账号。

不把整个 `OPENCLAW_STATE_DIR` 同时挂给两个现有完整实例直接使用。第一阶段不必先把全部存储改成 PostgreSQL：可以保留本地文件作为业务存储，在完成路径解耦、启动副作用审计和单写者交接之后再复用。若某插件不能遵守单写者约束，必须阻止该部署组合或先补齐插件契约。

不要在旧实例仍写入时复制一份 sessions/workspace 给新实例并立即切换。预热快照只用于检查，正式接管必须读排空后的最终状态；任何持久化绝对路径也需校验。

### 3.2 待命模式与执行权

拟新增 `STANDBY → ACTIVE → DRAINING → RETIRED` 生命周期：

- STANDBY 可以检查产物、加载无副作用的组件、验证配置及预热独立缓存。
- STANDBY 不接受生产执行请求，不启动生产渠道、cron、heartbeat、投递恢复、工作区写入或迁移。
- 执行权由协调器持久化记录，包含实例标识与递增代次；写入和后台启动必须检查有效归属。
- 旧实例排空完成并释放执行权后，新实例才能激活。不能仅凭租约超时就假设旧实例已经停止写入；必须有隔离旧进程或拒绝旧代次写入的措施。
- 协调器或新实例失败时，不出现两个 active；以持久化阶段记录恢复，而不是猜测上一次脚本运行到了哪里。

单机文件锁可以作为执行权互斥的组成部分，但不能代替全部恢复、代次和副作用控制逻辑。只设置 `OPENCLAW_SKIP_CHANNELS` 或 `OPENCLAW_SKIP_CRON` 不构成完整待命模式。

### 3.3 消息入口与连接

普通反向代理只改变新连接的路由。已有 WebSocket 仍绑定旧后端，其中发来的下一条消息也仍到旧实例，因此必须覆盖所有生产入口，不能只修改 HTTP upstream。

第一阶段业务保证：入口先持久化消息再确认接收，以稳定 requestId、agentId、sessionKey 和用户身份关联请求；切换期间排队，交接后按会话顺序执行。记录接收、执行、完成、投递状态，设置容量、超时与背压规则。未知结果的工具调用不能无条件重试；外部系统支持时使用其幂等键，否则进入核对或人工处理。

连接目标分两档，实施前明确选择：

1. **允许短暂自动重连**：客户端保留未确认消息，按同一 requestId 查询结果或重试，并恢复历史与运行状态；完成回归后才能承诺消息不丢。
2. **严格不掉线**：新增稳定的 Gateway 协议入口，终止客户端 WebSocket、维护认证与订阅、请求关联、事件序号及恢复，再连接具体后端。它不是普通 WebSocket 代理配置，属于单独开发范围。

本方案以“业务消息不丢、会话连续”为第一阶段目标；若要求连接本身也从不断开，必须把第二档纳入实施范围。

Telegram 等轮询渠道、平台长连接和插件自有 webhook 不一定经过统一网页入口。需要通过通用插件契约暂停新消息消费、保存游标、完成在途投递并交接。不能在核心写渠道名称特判。无法持久化或重放的来源，需要稳定接收层或明确无法达到无损切换验收，不能泛称所有渠道零中断。

## 4. 构建与产物改造

### 4.1 构建端

在独立、固定提交的构建环境执行；以下是现有命令，不代表已完成部署编排：

```powershell
pnpm install --frozen-lockfile
pnpm check
pnpm test
pnpm build
pnpm ui:build
```

以最终产物验证结果为准。若采用 npm 包，使用现有 pack/prepack 流程完成打包；该流程会再次构建，应将时间和资源预算放在 CI。部署前在目标环境副本安装并执行实际启动 smoke，不能认为 tgz 自带全部运行依赖。

发布清单至少包含：提交 SHA、版本、操作系统与架构、Node/pnpm 版本、锁文件摘要、产物摘要、包含的插件及依赖、构建检查结果、支持的状态格式和回滚兼容范围。

交付格式按实际运行平台选择：

- 原生 Windows：在匹配的 Windows/架构环境准备并验证完整运行目录，检查原生模块与 pnpm 链接是否仍有效；不能直接复制来自其他平台的 node_modules。
- 已使用 Linux 容器：复用现有多阶段 Dockerfile，在构建端生成镜像，部署端按不可变摘要拉取。采用容器不是本方案前提，也不能假设当前电脑已安装 Docker。

产物应覆盖入口、dist、Control UI、生产依赖、插件及其运行依赖、模板和运行所需资源。以 `package.json` 的发布文件清单、Dockerfile 运行层和实际 smoke 共同核对，不能把这个列表当作未经验证的完整打包实现。

### 4.2 部署端

- 解压或拉取到新版本目录，校验清单，不在当前服务目录执行 `git pull`、依赖安装或 build。
- 用明确的版本入口和独立配置启动，不使用可能修改全局安装的升级命令替代蓝绿发布。
- 先验证运行环境、磁盘与内存余量，再启动 STANDBY。镜像解压、病毒扫描、模块加载和预热仍有资源开销，应限速和监控。
- `NODE_OPTIONS` 的堆限制不是整个进程或机器的 CPU/内存隔离；根据实际 Windows 服务或容器管理方式配置限制。
- 保留旧产物与发布阶段日志，清理只能发生在回滚窗口结束以后。

如果只有一台物理电脑且没有外部构建环境，可以在独立构建目录或容器中限资源构建，但不能承诺构建完全不影响线上延迟；需用压测结果决定是否可接受。

## 5. 发布顺序与失败处理

| 阶段 | 操作 | 失败处理 |
| --- | --- | --- |
| 准备 | 接收并校验产物，检查兼容性和资源 | 旧实例照常服务，丢弃未激活候选 |
| 待命 | 启动新实例，完成无生产副作用的检查与预热 | 停止候选，不触碰旧实例 |
| 暂停派发 | 入口继续持久化接收，暂停新业务执行；暂停后台新任务与渠道新消费 | 若无法确认所有入口均受控，取消发布 |
| 排空 | 旧实例完成已接收的队列、对话、工具、投递及后台工作，落盘并确认 | 超时默认取消发布并恢复旧实例接收；不默认强杀 |
| 交接 | 持久化交接阶段，旧实例失去写入权；新实例获得新代次，失效缓存并读最终状态 | 保持消息排队，依据阶段记录恢复唯一持有者 |
| 激活 | 新实例启动渠道与后台服务，通过业务 readiness，恢复消息派发 | 先隔离新实例，按状态兼容性决定回退 |
| 退役 | 确认旧实例无业务运行和必须保留的连接，再停止旧实例 | 不让服务管理器把旧实例自动拉回 active |

排空判定不只检查 active task 数量；还包括所有已确认接收但未完成的排队消息、子任务、压缩、审批等待、外部作业、工具副作用和投递。长时间等待的任务需要可恢复记录，或明确阻止此次发布。不要沿用“等待 300 秒后中止”作为无损部署策略。

readiness 至少区分“待命检查完成”和“已拥有执行权且可处理业务”；健康探针成功不代表可以切流。部署控制接口应采用现有认证授权体系，不暴露未授权的激活或执行权接口。

### 回滚边界

- 新实例尚未执行生产请求：确认其释放执行权后，恢复旧实例及入口派发。
- 新实例已经产生新消息：旧版本必须能读取最新状态后才可回滚；不能直接恢复发布前备份，否则会丢掉新消息。
- 涉及不兼容状态迁移：不得进入本方案的无损热切换流程；先做向前/向后兼容设计，或使用单独迁移窗口。
- 外部工具已经执行的操作不能靠恢复会话文件撤销；必须保存执行结果并核对重试语义。

## 6. 建议实施拆分

| 工作项 | 主要关联位置 | 交付标准 |
| --- | --- | --- |
| 不可变构建产物与校验清单 | `scripts/build-all.mjs`、`scripts/openclaw-prepack.ts`、Dockerfile、后续部署脚本 | 构建失败不触碰线上；产物在目标平台副本可启动 |
| 独立待命、激活、排空、退役生命周期 | `src/gateway/server.impl.ts`、启动/关闭/runtime-services、`src/cli/gateway-cli/run-loop.ts` | 待命无生产副作用；停止与排空语义分离 |
| 执行权与状态交接 | `src/config/sessions/*`、`src/agents/session-write-lock.ts`、新增协调模块 | 任意时间仅一个业务写入者；最新历史和记忆可见 |
| 消息持久化与跨实例去重 | `src/process/command-queue.ts`、Gateway 请求路径、运行状态 | 已确认消息切换后仍可查询，重复请求不重复执行 |
| 渠道与后台单活 | Gateway 渠道生命周期、cron/heartbeat、插件公共契约 | 账号不双连接消费；任务与投递不重复 |
| WebSocket 恢复或稳定协议入口 | `ui/src/ui/gateway.ts`、Gateway 连接与事件路径 | 重连可恢复；若选严格连接连续档则入口独立维护连接 |
| 发布编排与恢复 | 新增部署控制脚本/服务 | 每个阶段失败都能恢复到唯一 active，发布过程可观测 |

这些是完整改造的代码定位建议，当前仅实现第 0 节列出的基础改动。实际涉及公共配置或 SDK 时，需要同步类型、schema、帮助、文档与相应基线生成流程；协议变化应保持兼容并补齐客户端。涉及安全 CODEOWNERS 路径的修改须由列出的 owner 明确请求或参与审查。第一阶段无需预先改动这些受限文件。

## 7. 上线验收

1. 旧实例持续接收测试请求时，在构建端构建失败或成功，旧实例状态均不被修改；部署机预热期间记录延迟、CPU、内存和磁盘占用。
2. 第 N 轮回答还在生成时开始发布，第 N+1 轮排队；接管后模型上下文包含第 N 轮已提交结果。检查 transcript 和实际请求上下文，而不只凭模型口头声称“记得”。
3. 会话 ID、agentId、路由策略、工作区和记忆文件在切换前后保持一致，摘要与长期记忆更新没有丢失或回退。
4. 相同 requestId 在切换前后重复提交，只产生一个逻辑执行结果；工具副作用按其幂等能力验收，不能仅检查聊天消息数。
5. 流式输出期间发布，当前回答完整结束；重连档验证请求恢复和 UI 历史，严格档另验证客户端连接全程保持及事件无缺漏。
6. 排空超过预算时发布取消，旧实例恢复接收；没有静默丢弃队列，也没有默认中止用户任务。
7. cron、heartbeat、渠道消费、投递恢复仅由持有执行权的实例启动；按实际启用插件逐个验证交接。
8. 在每个发布阶段模拟新实例失败、协调器重启及旧进程延迟退出，均不会产生双 active；已确认消息仍可恢复。
9. 新版本产生消息后回滚，保留这些消息；不兼容状态明确阻止回滚。长时间运行的任务和审批有可恢复状态或明确阻止发布。
10. 全流程使用目标操作系统与进程管理器测试；原生 Windows 不照搬 Unix 信号或关闭命令。

已确认部署形式与主要入口；实施完整编排前仍需核对其他后台插件及资源余量。第一阶段按允许自动重连设计，不承诺 TCP/WebSocket 连接始终不断开。以上验收全部通过以前，不能把方案标注为已支持零中断发布。
